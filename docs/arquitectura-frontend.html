01Panorama general

El frontend es una aplicación Flutter organizada bajo Clean Architecture con enfoque feature-first. Cada funcionalidad vive en su propia carpeta y se subdivide en tres capas con dependencias estrictamente unidireccionales. Toda la composición de objetos ocurre mediante Riverpod: no hay singletons globales ni instanciación directa entre capas.

Decisión de diseño

La autenticación no se implementa con un formulario propio de usuario y contraseña. Se delega en Keycloak mediante Authorization Code Flow con PKCE, abriendo el navegador del sistema. La app nunca ve las credenciales del usuario: solo recibe tokens. Esto es lo que exige el estándar OAuth 2.0 for Native Apps (RFC 8252) y es la razón de que exista el esquema com.quehaypa.app://oauth/callback registrado en el manifiesto de Android.

Principios que sostienen la estructura

  • Regla de dependencia. Las capas externas conocen a las internas, nunca al revés. presentation → domain ← data.
  • Inversión de dependencias. El dominio declara interfaces abstractas; la capa de datos las implementa. El dominio no sabe si detrás hay Dio, Keycloak o una base de datos local.
  • Un caso de uso, una intención. Cada UseCase expone un único método call(), de modo que se invoca como si fuera una función.
  • Estado inmutable. Los estados se modelan como clases con copyWith; nunca se mutan en sitio.
  • El widget no decide. La UI observa estado y despacha intenciones. Toda la lógica vive en el controlador y por debajo.

02Las tres zonas del código

Dentro de lib/ existen exactamente tres zonas, y cada archivo nuevo pertenece a una sola de ellas. Elegir mal la zona es el error estructural más frecuente.

ZonaQué contieneCriterio de pertenencia
app/ Arranque, configuración, router y los providers que cablean dependencias entre features. Aquí va lo que necesita conocer la aplicación completa. Si algo debe saber de dos features a la vez, va aquí.
core/ Infraestructura transversal: red, seguridad, errores. Sin lógica de negocio. Aquí va lo que cualquier feature podría usar y no pertenece a ninguna en particular.
features/ Una carpeta por funcionalidad de negocio, con sus tres capas dentro. Aquí va todo lo demás. Es el destino por defecto: ante la duda, va en la feature.

Nota sobre home

La feature home solo tiene capa de presentación. Es legítimo: una pantalla sin reglas de negocio ni acceso a datos no necesita domain/ ni data/. No cree capas vacías por simetría. Cree cada capa en el momento en que tenga contenido real.

03Clean Architecture en tres capas

Cada feature con lógica de negocio se divide en tres capas. La dirección de las flechas es la parte importante: el dominio es el centro y no depende de nada.

Responsabilidad exacta de cada pieza

Domain  Lógica de negocio pura

  • Entity — objeto de negocio. Sin fromJson, sin anotaciones, sin dependencias externas. Ejemplo real: AuthSession.
  • Repository (abstracto) — el contrato. Declara qué operaciones existen, jamás cómo se cumplen. Ejemplo: AuthenticationRepository.
  • UseCase — una acción del sistema. Recibe el repositorio por constructor y expone call(). Ejemplo: LoginUseCase.

Data  Cómo se cumple el contrato

  • Model — espejo del DTO externo. Aquí vive fromJson y el método toEntity() que traduce al dominio. Ejemplo: AuthSessionModel.
  • DataSource — el punto donde ocurre la E/S real. Traduce fallos técnicos a las excepciones de core/errors/exceptions.dart. Ejemplo: KeycloakDataSource.
  • RepositoryImpl — implementa la interfaz del dominio orquestando uno o varios datasources. Ejemplo: AuthenticationRepositoryImpl, que combina Keycloak con TokenManager.

Presentation  Lo que el usuario ve y toca

  • State — clase inmutable con copyWith. Ejemplo: AuthenticationState con su enum AuthenticationStatus.
  • Controller — un Notifier de Riverpod. Invoca casos de uso y traduce su resultado a estado. Nunca lanza excepciones hacia la UI: las captura y las convierte en un estado de error.
  • Page / Widget — ConsumerWidget. Solo observa (ref.watch) y despacha (ref.read(...notifier).accion()).
  • Providers — construyen el grafo de la feature: datasource → repositorio → casos de uso.

Por qué existen los puertos en core

El interceptor necesita renovar la sesión, pero core no puede importar features/authentication sin invertir la regla de dependencia. La solución aplicada es correcta: core declara las interfaces SessionRefresher y SessionInvalidator, la feature las implementa, y los providers de app/ hacen la unión. Replique este patrón cada vez que core necesite algo que solo una feature sabe hacer.

05Inyección de dependencias

No existe ningún service locator ni GetIt. Riverpod es el contenedor: cada objeto se declara una vez en un provider y se resuelve por composición.

Convención de resolución

Dentro del cuerpo de un Provider el proyecto usa ref.read, no ref.watch, porque son dependencias de construcción que no cambian durante la vida de la app. En cambio, en los widgets se usa ref.watch para que la UI reaccione.

Regla práctica

ref.watch en build() de widgets y cuando quiera reconstruir ante cambios. ref.read dentro de providers de construcción y en manejadores de eventos (onPressed). Usar watch en un onPressed es un error; usar read en un build deja la UI congelada.

06Flujo de autenticación

Es el flujo más elaborado del proyecto y el mejor ejemplo de cómo se atraviesan las tres capas. Conviene entenderlo antes de escribir un módulo nuevo.

Inicio de sesión

  1. LoginPage llama a ref.read(authenticationControllerProvider.notifier).login().
  2. El controlador pasa el estado a loading e invoca LoginUseCase().
  3. El caso de uso delega en AuthenticationRepository.login().
  4. AuthenticationRepositoryImpl llama a KeycloakDataSource.login().
  5. El datasource ejecuta authorizeAndExchangeCode: se abre el navegador del sistema, el usuario se autentica en Keycloak y el sistema devuelve el control a la app mediante el esquema com.quehaypa.app://oauth/callback.
  6. Se recibe AuthSessionModel; el repositorio persiste los tres tokens vía TokenManager y devuelve la entidad.
  7. El controlador pasa a authenticated.
  8. El cambio de estado despierta a RouterRefreshNotifier, GoRouter reevalúa su redirect y navega a /home.

Restauración al abrir la app

En initState de App se dispara restoreSession(). La lógica de AuthenticationRepositoryImpl.restoreSession() es escalonada:

  • Si no hay access token guardado → null (usuario no autenticado).
  • Si TokenManager.hasSession() confirma que el token sigue vigente → se reconstruye la sesión sin tocar la red.
  • Si el token caducó pero existe refresh token → se intenta refreshSession().
  • Si la renovación falla o no hay refresh token → se limpia el almacenamiento y se devuelve null.
Detalle de calidad

TokenManager._isExpired() decodifica el JWT en local y aplica un margen de 60 segundos antes del exp real. Así se evita el caso en que un token válido al enviarse expira en tránsito. Ante cualquier anomalía de decodificación devuelve true, es decir, asume caducidad: falla del lado seguro.

Cierre de sesión

logout() notifica el fin de sesión a Keycloak mediante endSession y limpia el almacenamiento local dentro de un bloque finally. Esto garantiza que los tokens locales desaparezcan aunque Keycloak esté inaccesible.

Expulsión por sesión inválida

Existe un camino independiente para cuando la sesión muere sin que el usuario lo pida:

AuthInterceptor (401 irrecuperable)
    └─> SessionInvalidator.invalidateSession()
            ├─> TokenManager.clearSession()
            └─> SessionEvents.notifySessionInvalidated()
                    └─> sessionInvalidatedProvider (Stream)
                            └─> AuthenticationController escucha en build()
                                    └─> state = unauthenticated
                                            └─> GoRouter redirige a /login

La consecuencia práctica es importante: cualquier módulo nuevo hereda esta protección gratis. Si su repositorio hace una petición con Dio y el backend responde 401 sin posibilidad de renovación, el usuario será expulsado a la pantalla de login sin que usted escriba una sola línea para ello.

07Renovación automática de tokens

AuthInterceptor es la pieza más delicada de core. Conviene no modificarla sin entender su control de concurrencia.

En cada petición saliente

onRequest lee el access token y, si existe, añade la cabecera Authorization: Bearer <token>. Si no hay token, la petición sale sin cabecera: es responsabilidad del backend rechazarla.

Ante un 401

  1. Si el código no es 401, el error se propaga sin tocarlo.
  2. Si la petición ya lleva la marca extra['retried'] == true, se propaga el error. Esto corta los bucles infinitos de reintento.
  3. Se marca la petición y se solicita un token renovado.
  4. Si la renovación devuelve un token válido, se reescribe la cabecera, se reintenta la petición original con dio.fetch y se resuelve como si nunca hubiera fallado. La capa que hizo la llamada no se entera del 401.
  5. Si la renovación falla, se invalida la sesión y el error se propaga.

Control de concurrencia: single-flight

Si cinco peticiones simultáneas reciben 401 a la vez, sería catastrófico lanzar cinco renovaciones en paralelo: Keycloak rota el refresh token y las renovaciones que llegan tarde fallarían, tumbando la sesión de un usuario perfectamente válido. El interceptor lo evita guardando el Future en curso:

lib/core/network/auth_interceptor.dart
Future<String?> _getRefreshedToken() {
    final refreshingToken = _refreshingToken;

    if (refreshingToken != null) {
        return refreshingToken;          // ya hay una renovación en vuelo
    }

    final refreshFuture = _refreshAccessToken();

    _refreshingToken = refreshFuture;

    refreshFuture.whenComplete(() {
        _refreshingToken = null;         // libera el carril al terminar
    });

    return refreshFuture;
}

Las peticiones que llegan mientras hay una renovación en vuelo se suscriben al mismo Future. Se ejecuta una sola renovación y todas reciben su resultado.

No romper esto

Si algún módulo nuevo necesita un cliente HTTP, debe obtenerlo de dioClientProvider. Crear un Dio() propio deja la petición sin cabecera de autorización, sin renovación automática y sin expulsión por sesión inválida. Es el error de integración más caro de diagnosticar.

08Enrutamiento y guardas

El router es un Provider<GoRouter>, lo que permite que lea el estado de autenticación sin acoplarse a ningún widget.

Mecanismo de reactividad

GoRouter no observa Riverpod por sí mismo. El puente es RouterRefreshNotifier, un ChangeNotifier de tres líneas:

ref.listen<AuthenticationState>(
    authenticationControllerProvider,
    (previous, next) {
        if (previous?.status != next.status) {
            routerRefreshNotifier.refresh();   // -> notifyListeners()
        }
    },
);

Solo se notifica cuando cambia el status, no ante cualquier cambio del estado. Evita reevaluaciones inútiles del redirect.

La guarda

SituaciónResultado
Estado initial o loadingnull — no se redirige. Espera a que se resuelva la restauración de sesión.
No autenticado y va a una ruta distinta de /loginRedirige a /login.
Autenticado y va a /loginRedirige a /home.
Restonull — navegación permitida.
Consecuencia para módulos nuevos

La guarda es excluyente por defecto: toda ruta que no sea /login exige sesión activa. Al añadir /events o /profile queda protegida automáticamente. Solo tendrá que modificar el redirect si necesita una ruta pública, y entonces conviene sustituir la comparación literal con /login por una lista de rutas públicas.

Gate de arranque

Mientras el estado sea initial, el builder de MaterialApp.router sustituye toda la pantalla por un CircularProgressIndicator. Es lo que impide el parpadeo de la pantalla de login antes de saber si hay sesión guardada.

El host es inyectable en tiempo de compilación

El host de la API y de Keycloak no está escrito a mano. Se declara una sola vez y se lee del entorno de compilación, con localhost como valor por defecto:

lib/app/config/app_config.dart
static const _host = String.fromEnvironment(
    'BACKEND_HOST',
    defaultValue: 'localhost',
);

static const _realm = 'http://$_host:9090/realms/que-hay-pa-dev';

static const development = AppConfig(
    environment: Environment.development,
    apiBaseUrl: 'http://$_host:8080',
    keycloakIssuer: _realm,
    keycloakClientId: 'que-hay-pa-mobile',
    keycloakRedirectUrl: 'com.quehaypa.app://oauth/callback',
    keycloakEndSessionUrl:
        '$_realm/protocol/openid-connect/logout',
);

La constante _realm existe para que la URL del realm aparezca una única vez: el issuer y la URL de cierre de sesión se derivan de ella y no pueden desincronizarse. Como _host es const, la interpolación sigue siendo constante y AppConfig.development conserva su constructor const.

EscenarioComando
Escritorio o web (mismo equipo)flutter run -d windows
Emulador Android--dart-define=BACKEND_HOST=10.0.2.2
Dispositivo físico--dart-define=BACKEND_HOST=<IP LAN del PC>
Bloqueante en dispositivo físico

Desde un teléfono, localhost es el propio teléfono, no el PC de desarrollo. Si se omite --dart-define, la app arranca pero el login falla siempre. Además hay que asegurarse de que backend y Keycloak escuchan en 0.0.0.0 y abrir los puertos 8080 y 9090 en el cortafuegos.

Qué NO es --dart-define

No es una variable de entorno del sistema: String.fromEnvironment se resuelve al compilar, no al ejecutar. De ahí dos consecuencias prácticas: el hot reload no recoge un valor nuevo (hay que relanzar flutter run), y el valor queda incrustado en el binario, extraíble de un APK sin dificultad. Sirve para configuración, nunca para secretos.

Pendiente en el entorno actual

app_config_provider.dart devuelve AppConfig.development de forma fija y no existe una constante production. Antes de cualquier publicación hay que definirla, sin allowInsecureConnections y sobre HTTPS.

10Deuda técnica detectada

Hallazgos verificados sobre el código actual. Ninguno impide compilar, pero todos conviene resolverlos antes de que el proyecto crezca.

HallazgoGravedadDetalle y acción
data/auth_service.dart sin uso Media Clase AuthService con el issuer, el clientId y el redirectUrl escritos a mano, duplicando lo que ya hace KeycloakDataSource a partir de AppConfig. Ninguna referencia la usa. Es una versión anterior que quedó huérfana y que, si alguien la retoma, reintroducirá localhost por la puerta de atrás. Eliminar.
core/security/keycloak_session_refresher.dart vacío Baja Archivo de 0 bytes. Su función la cumple SessionRefresherImpl. Eliminar.
core/errors/failtures.dart Media Dos problemas: el nombre está mal escrito (failtures → failures) y ninguna de las seis clases Failure se usa en el proyecto. Hay que decidir: adoptar el patrón Either<Failure, T> de forma consistente, o eliminarlo y quedarse solo con excepciones. Convivir con ambos es lo peor de los dos mundos.
copyWith no puede limpiar campos Media En AuthenticationState.copyWith, errorMessage ?? this.errorMessage hace imposible volver a null pasando null. Un mensaje de error puede quedar pegado en estados posteriores. Se resuelve con centinelas o con freezed.
Mensajes de excepción expuestos en la UI Alta
(en producción)		 Las excepciones de core/errors/exceptions.dart ya sobrescriben toString(), de modo que el mensaje real llega a la pantalla en lugar de Instance of '...'. Eso es lo correcto en desarrollo, pero KeycloakDataSource compone el texto como '... : $e', incluyendo la excepción cruda de AppAuth con URLs y puertos internos. Mostrado al usuario final es fuga de información. Antes de publicar: conservar el toString() completo para los logs y mapear a mensajes genéricos en la UI.
Proyecto sin control de versiones efectivo Alta El repositorio existe y tiene remoto configurado, pero git ls-files devuelve cero archivos rastreados: solo se había subido un README.md. Todo el código fuente vive únicamente en el disco local, sin historial, sin posibilidad de revertir y sin respaldo.
local.properties no está en .gitignore Media android/local.properties contiene rutas absolutas propias de cada máquina (sdk.dir, flutter.sdk). Versionarlo rompe la compilación de cualquier otro desarrollador con un error engañoso. Debe excluirse explícitamente: la plantilla de Flutter no lo hace.
Permiso INTERNET ausente en release Alta El manifiesto principal no lo declara; solo lo tienen los de debug y profile. Un APK de release no tendría acceso a red. Añadir <uses-permission android:name="android.permission.INTERNET"/> a src/main/AndroidManifest.xml.
usesCleartextTraffic="true" Alta Necesario hoy porque el backend es HTTP plano. Debe desactivarse antes de publicar, junto con allowInsecureConnections en el datasource.
applicationId de plantilla Media Sigue siendo com.example.frontend. Google Play rechaza el prefijo com.example. Cambiar a com.quehaypa.app antes de la primera publicación (después es irreversible).
Firma de release con clave de depuración Alta signingConfig = signingConfigs.getByName("debug"). Hay que generar un keystore propio antes de distribuir.
Sin pruebas Media Solo existe widget_test.dart de plantilla. La arquitectura está preparada para pruebas (todo se inyecta), pero no se aprovecha: los casos de uso y repositorios son triviales de cubrir con dobles.

11Cómo agregar un módulo nuevo

Procedimiento normalizado en nueve pasos. Como ejemplo se construye un módulo events que lista los eventos disponibles consumiendo GET /events de la API. Sustituya Event por su entidad y el resto es mecánico.

Estructura a crear

lib/features/events/ ├── domain/ │ ├── entities/event.dart │ ├── repositories/event_repository.dart │ └── usecases/get_events_use_case.dart ├── data/ │ ├── models/event_model.dart │ ├── datasources/event_remote_data_source.dart │ └── repositories/event_repository_impl.dart └── presentation/ ├── controllers/ │ ├── events_state.dart │ ├── events_controller.dart │ └── events_providers.dart └── pages/events_page.dart
Orden de trabajo

Construya de dentro hacia afuera: primero el dominio, luego los datos, al final la presentación. Así el compilador le va guiando y nunca escribe una capa contra un contrato que todavía no existe.

1
Definir la entidad domain/entities/event.dart

Objeto de negocio puro. Sin JSON, sin Flutter, sin anotaciones.

class Event {
    final String id;
    final String title;
    final String description;
    final DateTime startsAt;
    final String location;

    const Event({
        required this.id,
        required this.title,
        required this.description,
        required this.startsAt,
        required this.location,
    });
}
2
Declarar el contrato del repositorio domain/repositories/event_repository.dart

Qué operaciones existen. Nunca cómo se cumplen.

import '../entities/event.dart';

abstract class EventRepository {
    Future<List<Event>> getEvents();

    Future<Event> getEventById(String id);
}
3
Escribir el caso de uso domain/usecases/get_events_use_case.dart

Una intención, un call(). Se invoca como una función.

import '../entities/event.dart';
import '../repositories/event_repository.dart';

Aquí solo delega, igual que LoginUseCase. Su valor aparece cuando hay reglas: filtrar eventos pasados, ordenar por cercanía, combinar dos repositorios. Ese es exactamente el sitio donde debe ir esa lógica — no en el controlador ni en el widget.

import '../../domain/entities/event.dart';

class EventModel {
    final String id;
    final String title;
    final String description;
    final DateTime startsAt;
    final String location;

    const EventModel({
        required this.id,
        required this.title,
        required this.description,
        required this.startsAt,
        required this.location,
    });

    factory EventModel.fromJson(Map<String, dynamic> json) {
        return EventModel(

            title: json['title'] as String,
            description: json['description'] as String? ?? '',
            startsAt: DateTime.parse(json['startsAt'] as String),
            location: json['location'] as String? ?? '',
        );
    }

    Event toEntity() {
        return Event(
            id: id,
            title: title,
            description: description,
            startsAt: startsAt,
            location: location,
        );
    }
}
5
Implementar el datasource remoto data/datasources/event_remote_data_source.dart

Aquí ocurre la E/S real. Recibe DioClient por constructor — jamás construye su propio Dio — y traduce los fallos técnicos a las excepciones de core/errors/exceptions.dart.

import 'package:dio/dio.dart';

import '../../../../core/errors/exceptions.dart';
import '../../../../core/network/dio_client.dart';
import '../models/event_model.dart';

class EventRemoteDataSource {
    final DioClient _dioClient;

    const EventRemoteDataSource({
        required DioClient dioClient,
    }) : _dioClient = dioClient;

    Future<List<EventModel>> getEvents() async {
        try {
            final response = await _dioClient.dio.get<List<dynamic>>(
                '/events',
            );

            final data = response.data;

            if (data == null) {
                throw const ServerException(
                    'La respuesta de /events vino vacia.',
                );
            }

            return data
                .cast<Map<String, dynamic>>()
                .map(EventModel.fromJson)
                .toList();
        } on DioException catch (e) {
            if (e.response?.statusCode == 401) {
                throw const UnauthorizedException(
                    'Sesion no valida.',
                );
            }

            throw NetworkException(
                'No fue posible obtener los eventos: ${e.message}',
            );
        }
    }
}
Punto crítico de integración

La línea _dioClient.dio.get(...) es lo que conecta su módulo con toda la infraestructura de sesión: cabecera Bearer automática, renovación transparente ante un 401 y expulsión a /login si la sesión murió. Un Dio() propio pierde las tres cosas.

Implementar el repositorio data/repositories/event_repository_impl.dart

Cumple el contrato del dominio orquestando los datasources y traduciendo modelos a entidades.

import '../../domain/entities/event.dart';
import '../../domain/repositories/event_repository.dart';
import '../datasources/event_remote_data_source.dart';

class EventRepositoryImpl implements EventRepository {
    final EventRemoteDataSource _remoteDataSource;

    const EventRepositoryImpl({
        required EventRemoteDataSource remoteDataSource,
    }) : _remoteDataSource = remoteDataSource;

    @override
    Future<List<Event>> getEvents() async {
        final models = await _remoteDataSource.getEvents();

        return models.map((model) => model.toEntity()).toList();
    }

    @override
    Future<Event> getEventById(String id) async {
        final model = await _remoteDataSource.getEventById(id);

        return model.toEntity();
    }
}

Modelar el estado y el controlador presentation/controllers/

Mismo patrón que AuthenticationState: enum de estatus más clase inmutable.

events_state.dart
import '../../domain/entities/event.dart';

enum EventsStatus { initial, loading, loaded, error }

class EventsState {
    final EventsStatus status;
    final List<Event> events;
    final String? errorMessage;

    const EventsState({
        required this.status,
        this.events = const [],
        this.errorMessage,
    });

    const EventsState.initial()
        : status = EventsStatus.initial,
            events = const [],
            errorMessage = null;

    EventsState copyWith({
        EventsStatus? status,
        List<Event>? events,
        String? errorMessage,
    }) {
        return EventsState(
            status: status ?? this.status,
            events: events ?? this.events,
            errorMessage: errorMessage,
        );
    }
}
Mejora aplicada

Fíjese en errorMessage: errorMessage sin ??. Corrige el problema señalado en §10: aquí sí se puede limpiar el mensaje de error pasando null.

events_controller.dart
import 'package:flutter_riverpod/flutter_riverpod.dart';

import '../../domain/usecases/get_events_use_case.dart';
import 'events_providers.dart';
import 'events_state.dart';

final eventsControllerProvider =
    NotifierProvider<EventsController, EventsState>(
        EventsController.new,
    );

class EventsController extends Notifier<EventsState> {
    late final GetEventsUseCase _getEventsUseCase;

    @override
    EventsState build() {
        _getEventsUseCase = ref.read(getEventsUseCaseProvider);

        return const EventsState.initial();
    }

    Future<void> loadEvents() async {
        state = state.copyWith(
            status: EventsStatus.loading,
            errorMessage: null,
        );

        try {
            final events = await _getEventsUseCase();

            state = state.copyWith(
                status: EventsStatus.loaded,
                events: events,
            );
        } catch (e) {
            state = state.copyWith(
                status: EventsStatus.error,
                errorMessage: e.toString(),
            );
        }
    }
}

El controlador nunca deja escapar una excepción. Todo fallo se convierte en un estado que la UI sabe representar.

Detalle de tipado

Provider<EventRepository> declara el tipo de la interfaz, no el de la implementación. Así, quien consuma el provider no puede acoplarse por accidente a EventRepositoryImpl, y sustituirla en pruebas es inmediato.

import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

import '../controllers/events_controller.dart';
import '../controllers/events_state.dart';

class EventsPage extends ConsumerStatefulWidget {
    const EventsPage({super.key});

    @override
    ConsumerState<EventsPage> createState() => _EventsPageState();
}

class _EventsPageState extends ConsumerState<EventsPage> {
    @override
    void initState() {
        super.initState();

        Future.microtask(() {
            ref.read(eventsControllerProvider.notifier).loadEvents();
        });
    }

    @override
    Widget build(BuildContext context) {
        final state = ref.watch(eventsControllerProvider);

        return Scaffold(
            appBar: AppBar(
                title: const Text('Eventos'),
            ),
            body: switch (state.status) {
                EventsStatus.loading =>
                    const Center(child: CircularProgressIndicator()),

                EventsStatus.error => Center(
                    child: Text(
                        state.errorMessage ?? 'Ocurrio un error.',
                    ),
                ),

                EventsStatus.loaded => ListView.builder(
                    itemCount: state.events.length,
                    itemBuilder: (context, index) {
                        final event = state.events[index];

                        return ListTile(
                            title: Text(event.title),
                            subtitle: Text(event.location),
                        );
                    },
                ),

                _ => const SizedBox.shrink(),
            },
        );
    }
}
Por qué Future.microtask

Modificar un provider durante la fase de construcción del widget lanza un error en Riverpod. Aplazar la llamada al siguiente ciclo del bucle de eventos evita el conflicto. Es el mismo recurso que emplea App.initState para restoreSession().

12Checklist y convenciones

Antes de integrar un módulo

  • El dominio no importa flutter, dio ni dart:io.
  • El repositorio está tipado como interfaz en su provider, no como implementación.
  • El datasource obtiene el cliente HTTP de dioClientProvider.
  • Ningún Dio() instanciado fuera de DioClient.
  • No hay URLs literales fuera de AppConfig.
  • Los fallos técnicos se traducen a las excepciones de core/errors/exceptions.dart.
  • El controlador captura toda excepción y la convierte en estado.
  • El estado es inmutable y su copyWith permite limpiar campos opcionales.
  • La UI usa ref.watch en build y ref.read en manejadores.
  • La ruta está registrada en los tres archivos del router.
  • flutter analyze termina sin advertencias.

13Errores comunes

ErrorSíntomaSolución
Instanciar Dio() en el datasource Respuestas 401 constantes pese a haber iniciado sesión Inyectar DioClient desde dioClientProvider.
Importar data/ desde domain/ Compila, pero la arquitectura queda invertida y el dominio deja de ser testeable El dominio solo importa de sí mismo. Si necesita algo de fuera, decláralo como interfaz.
Poner reglas de negocio en el widget Lógica imposible de probar sin levantar la UI Trasladarla al caso de uso.
ref.watch dentro de onPressed Excepción en tiempo de ejecución o reconstrucciones descontroladas ref.read en manejadores de eventos.
Llamar al controlador directamente en build «Tried to modify a provider while the widget tree was building» Envolver en Future.microtask desde initState.
Devolver el Model hacia la UI Un cambio en el JSON del backend rompe los widgets Convertir siempre con toEntity() en el repositorio.
Olvidar registrar la ruta en los tres archivos Pantalla en blanco o error de ruta no encontrada route_paths, route_names y app_router.
Escribir la URL en el datasource Imposible cambiar de entorno sin editar código Solo rutas relativas: baseUrl ya viene de AppConfig.
Capturar excepciones en la página Estados inconsistentes y errores duplicados El controlador es el único que captura; la página solo lee el estado.
